# Search architecture

This first implementation keeps the existing movie search working and introduces
a persistent runtime. It does not yet ingest books, PDFs, or EPUB files, or generate
answers from retrieved passages.

## Current execution flow

```text
CLI client -> HTTP handler -> SearchService -> HybridSearch
                              |                |-- BM25Retriever
                              |                `-- SemanticRetriever
                              |-- optional QueryEnhancer
                              `-- optional IndividualLLMReranker

QueryEnhancer / IndividualLLMReranker -> LLMClient protocol -> SDK adapter
```

`rag_search/app/bootstrap.py` is the composition root: it loads configuration and source data,
prepares compatible indexes, constructs the adapters, and connects the components.
`SearchRuntime` owns the initialized collections and closes shared clients on exit.
The server creates its runtime once before serving requests. Local CLI commands
create one runtime for their invocation; remote CLI commands load no search models.

The package is organized by responsibility. Shared result contracts live in
`rag_search/search_models.py`, so clients do not import the search service to use its data.

| Location | Responsibility |
| --- | --- |
| `cli/` | CLI arguments and dispatch to command functions |
| `api/search_server.py` | FastAPI routes, application factory, and startup/shutdown lifecycle |
| `api/search_client.py` | Typed requests and pooled HTTP connections |
| `api/schemas.py` | Shared HTTP contracts and validation |
| `rag_search/commands/` | Implement console operations selected by the CLI |
| `rag_search/app/` | Construct dependencies and own their lifetime |
| `rag_search/config/` | Settings code, defaults, collection configuration, and prompt files together |
| `rag_search/search/` | Keyword/semantic indexes, fusion, enhancement, and reranking |
| `rag_search/llm/` | Application-owned LLM contract and SDK implementations |
| `rag_search/sources/` | Read source data into the application |
| `rag_search/search_models.py` | Shared request-independent result structures |

`cli/hybrid_search_cli.py` owns its argument parser and dispatch. Its command
functions and formatting are in `rag_search/commands/hybrid_search_commands.py`.
Keyword and semantic commands follow the same split. The reusable query workflow
is `SearchService.search` in `rag_search/search/search_service.py`. Search algorithms
and the application workflow have no dependency on CLI or HTTP code.

Search modules use descriptive names such as `hybrid_search.py`,
`semantic_search.py`, and `query_enhancer.py`. `retrievers.py` contains the small
`Retriever` protocol and `BM25Retriever` / `SemanticRetriever` adapters. The semantic
adapter is named after its operation, while the selected collection/source belongs
to startup configuration.

All HTTP code is centralized in `api/`. `create_app(runtime_factory)` constructs a
FastAPI application without loading indexes during import. Its lifespan creates
one runtime before serving requests, then closes shared clients on shutdown.
Synchronous query routes run in the framework's thread pool; index preparation
and client cleanup are also dispatched off the event loop.

`SearchRequest` and response models in `api/schemas.py` define validation and the
OpenAPI contract. The Python client uses those same models and owns a reusable
HTTPX connection pool. It validates responses before returning domain results.
Externally injected HTTP clients retain their caller-owned lifetime. The CLI
closes its pool after its request.

Successful search payloads retain their existing shape. Invalid request bodies
now return structured HTTP 422 errors; missing collections return 404, unavailable
LLM features return 503, and upstream LLM errors return 502. `/docs` and
`/openapi.json` are generated by FastAPI. Uvicorn serves the ASGI application.

## Resource reuse and concurrency

Source data, indexes, and the embedding model remain resident in a server process.
Each query generates only its query embedding and retrieves/reranks candidates.
The BM25 query path does not reload files or add unknown query terms to its index.
Semantic queries serialize access to the shared embedding model with a lock.
Prompts and results are constructed locally per request rather than held in
mutable shared prompt dictionaries.

The API uses FastAPI and Uvicorn. Runtime construction and shutdown follow the
application lifespan pattern described in [the FastAPI documentation](https://fastapi.tiangolo.com/advanced/events/).
Multiple processes each load their own copy of the model and indexes, so begin
with one worker. The application workflow remains independent of ASGI and HTTP.

## Ranking and result contracts

Enhancement produces an effective query that is passed to both retrievers and the
reranker. Query expansion appends terms to the original query. Both the original
and effective query are returned to the caller.

Scores retain full precision internally. Console formatting controls displayed
precision. Full descriptions remain available for all movie candidates, including
semantic-only hits; `display_doc` contains a short preview.

Retrieval and reranking depths are separate. With the default constants, a request
for five results retrieves up to 2,500 candidates from each retriever. Individual
reranking scores up to 25 fused candidates and returns five. Previously the
candidate multipliers compounded to 12,500 per retriever in that case. The ordinary
search retrieval depth is preserved; reranking no longer multiplies it again.
Evaluate retrieval depth against representative queries before reducing it for
speed. Constants live in `rag_search/config/defaults.py`.

Only individual reranking is currently exposed. Unsupported methods are rejected
rather than silently returning unreranked results. A future reranker can implement
the small `Reranker` protocol and be injected during setup; request options can be
expanded when another strategy is actually supported.

## Collection prompt policy

Each collection explicitly selects a prompt profile in `rag_search/config/collections.toml`.
For example, the movies collection selects `movies`, which loads the four system
prompts from `rag_search/config/prompts/movies.toml`. A `documents` profile supplies different
instructions for passage relevance and document questions. This is explicit
configuration; no extra LLM call guesses the query's domain.

Startup resolves `Settings.collection(name)`, loads an immutable `PromptProfile`,
and injects it into `QueryEnhancer` and `IndividualLLMReranker`. Those feature
classes contain processing and validation logic, while the profile contains the
system instructions. Prompts are passed verbatim, so JSON braces in prompts are
not interpreted as string templates. Queries and retrieved text remain separate
user-message data.

The profile loader requires nonblank text for `enhancement.spell`,
`enhancement.rewrite`, `enhancement.expand`, and `reranking.individual`. Missing or
invalid settings fail before expensive index/model initialization. Profile files
are not read per query, and prompt changes do not invalidate retrieval indexes.
Restart to pick up new instructions. Response types and score bounds remain
application contracts enforced by code.

Currently only the movies collection is loaded. A future book collection can
select the documents profile or a custom profile when its reader and passage
indexing are implemented. Adding a TOML entry alone does not implement ingestion.

## LLM boundary

Search features receive an `LLMClient` and work with response strings, never SDK
message or completion types. Text enhancement and JSON relevance scoring request
different output modes. The reranker parses and validates the score, rejecting
malformed output, booleans, nonnumeric values, nonfinite values, and values outside
0–10. Transport and incomplete-response failures become `LLMError`.

`rag_search/llm/openai_compatible_client.py` contains the existing adapter.
`client_factory.py` selects it from `LLM_BACKEND`; bootstrap and the manual smoke
check both use this factory. A native provider SDK gets a separate adapter and a
builder registered there. Features require `complete(...) -> str`; adapters owned
by the runtime additionally implement `close()`. Each backend controls its own
credential rules, including support for libraries that do not use API keys.
See [the adapter guide](llm_adapters.md) for extension steps. Model capabilities and provider-specific options
belong inside the adapter/configuration boundary. A single universal parameter
set is not assumed to work with every model.

The SDK's JSON mode produces JSON rather than enforcing the relevance-score schema,
so validation remains in the reranker. See the [official OpenAI documentation](https://developers.openai.com/api/docs/guides/structured-outputs)
for JSON mode and schema-based structured output.

## Index persistence

The persistent movie application uses `cache/collections/movies/`, leaving existing
standalone keyword/semantic CLI caches separate. Its manifest records source content
and ordering, stopwords, embedding model ID, chunking configuration, and an index
format version. Startup rebuilds both retrieval indexes when those inputs change
or required files are missing. BM25 and semantic search use the same loaded dataset.

Source/configuration changes become visible after restart. Simultaneous writers,
incremental indexing, and live collection replacement are future work. Model IDs
that refer to mutable remote revisions are not content-pinned by this manifest.

## Next step: information inside documents

Before adding book readers, introduce the following shared models in a separate
ingestion change, with movie records converted through a movie reader:

- `Document`: stable ID, title, source reference, and metadata.
- `Passage`: stable ID, parent document ID, text, order, and available page/section locations.
- `SearchHit`: the matching passage and source references alongside retrieval/reranking scores.

Readers should extract content and provenance. A chunker should produce passages.
Index preparation should build both BM25 and semantic indexes over those same
passages. Fusion should match passage IDs, preserve the matching text, and group
results by parent document only after retrieval when the presentation requires it.

The current semantic index returns document-level results by aggregating chunk
matches. `SemanticRetriever` adapts that index without choosing a domain. Book
questions will need passage-level results that preserve the matching text and its
location, rather than immediately aggregating all passages into one book result.

Add plain-text ingestion first to validate those contracts, followed by PDF/EPUB
readers. OCR for scanned pages is a separate extraction capability. New collections
can be registered in the runtime without changing the HTTP client's query shape.
An optional answer-generation stage can later consume retrieved passages and
source references to produce answers with citations.
